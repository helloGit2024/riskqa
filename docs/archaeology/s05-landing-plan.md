## 04 语义层设计：整个平台的“指标宪法”

语义层是平台里唯一业务与数据共签的合同。它的设计质量直接决定 Agent 的回答可不可信——因为 Agent 的一切数字都经由它定义。

### 4.1 分段所有权：谁写哪一段

| YAML 段落 | 内容 | Owner | 风控例子 |
|---|---|---|---|
| synonyms | 口语 → 标准名映射 | 业务 | “烂客户” → is_bad |
| dimensions | 维度清单与口径 | 业务定清单，数仓定映射 | vintage = 放款月（隐性维度显式化） |
| metrics.expr | 指标公式 | 业务给公式，数仓确认可实现 | fpd30 = 首期 DPD30+ 占比；分母是放款申请数 |
| tables / joins | 物理映射、关联路径、聚合粒度 | 数仓 | base_table: `<事实表占位>` |
| tests | 黄金题集（验收） | 双方 | “2026-08 各渠道 FPD30” 的标准答案 |

### 4.2 指标卡：每一行口径都要能回答“谁拍的”

```yaml
# 生产形态等价于 semantic_view.yaml，Owner 逐条签字后入库
"fpd30_rate": {
    "desc":      "首期逾期率：放款客户中首期 DPD30+ 的占比",
    "unit":      "ratio",
    "dims":       ["channel", "product", "vintage"],
    "calc":      "fpd30_rate",        # 绑定 M3 纯函数名
    "owner":     "风控策略组",         # ← 定义权在人
    "signed_at": "2026-09-30",
    "changelog": [("2026-09-30", "v1.0", "初版：放款后 30 天 DPD30+，宽限期 3 天")]
}
```

三个字段是监管视角的硬要求：owner（口径可追溯）、signed_at（变更留痕）、changelog（历史报告可复现解释）。KS 口径说改就改而无留痕，等于让全部历史报告失效——这在模型风险管理里是重大缺陷。

### 4.3 口径考古：LLM 当考古队长，人当拍板人

团队现状通常是口径躺在 30 个老脚本、若干 Excel 和历史报告里，无人认领。正确启动顺序：

1. 扫描存量：老代码/Excel/历史报告/数据字典，LLM 提取候选口径，每条必须带可核验证据链（文件 + 行号 + 原文片段），无证据的条目一律丢弃，不许补全；
2. 冲突检测：同一指标多个定义，原样列出，禁止 LLM 合并——“分母是提交数还是通过数”这种冲突，合成版一定是错的；
3. 生成问题清单：把冲突点和空白点变成给 Owner 的具体问题（“FPD30 在 `<脚本>:<行>` 与 `<指标字典>页` 定义不同，以哪个为准”）；
4. 签字入库：Owner 逐条裁决，双方签字后才合入 YAML。合入闸：无签字，代码层面禁止进正式文件。

#### 四个验收指标

证据率（有可核验出处口径 / 总口径，要求趋近 100%）、冲突清零率（已裁决 / 发现的总冲突，要求 100%）、考古发现率（扫出的“此前没人知道的对不上”数量）、人审耗时（单条 < 2 分钟，否则说明问题清单写得不好）。
