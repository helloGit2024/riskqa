# ADR-XXXX：【一句话说明这个决策】

> **什么时候写 ADR**：当你做了一个"以后可能想推翻、或者别人会问为什么这样做"的决定时。
> 例：选了哪个数据库、为什么不用某个流行框架、为什么先不做某个功能。
>
> **不用写 ADR**：改个变量名、修个 bug。

---

## 一、背景

⚙️ 当时面临什么情况？有哪些限制条件（时间 / 人力 / 预算 / 已有技术栈）？

## 二、备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. ⚙️ | | |
| B. ⚙️ | | |
| C. 什么都不做 | | |

> **方案 C 必须写。** "什么都不做"永远是一个真实选项，而且经常是对的。

## 三、决策

我们选择 **{{方案}}**。

## 四、理由

⚙️ 为什么是它，不是别的。**要具体到本项目的情况**，不许写"因为它更先进"。

## 五、代价（**必填，不允许留空**）

⚙️ 选它要承担什么？例：
- 多一个组件要维护
- 并发上不去，超过 N 人时要重做
- 以后要换的话，大概要动哪几块

> ⚠️ 这一节留空 = 这份 ADR 没写。**只写优点的决策记录是没有价值的**。

## 六、复核条件

⚙️ 什么情况下应该重新考虑这个决定？例："当单表超过 1000 万行时"、"当要支持多人同时在线超过 20 人时"。

## 七、★ 作为不懂技术的人，我只需要确认哪一点？

⚙️ 用大白话写一句话，让非技术的人能判断"我能不能接受这个代价"。
例：*"这个选择意味着前期能省两周，但将来人多了要重做一次。"*

> **这一节是这份模板真正的用途** —— 写决策记录不是为了技术存档，是为了让拍板的人能看懂。
