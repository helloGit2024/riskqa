# ADR-0006：文件快照是指标数据的唯一正式来源（直连库仅限探索）

> 状态：已接受（2026-11-01）｜ 影响面：data-model、architecture §五、constraints §三

## 一、背景

指标数据两种来法：数仓 T+1 导出文件快照 / 直连数据库。V2 的 M2 数据层已实现快照 + manifest 血缘，且设计文档明确纪律："正式交付永远基于快照计算；直连库只允许探索性看数"。本 ADR 把该纪律固化为架构决策。

## 二、备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 文件快照为唯一正式来源（本决策） | 数字可复现（manifest sha256 + data_as_of）；报告可重跑；审计可回溯 | 数据 T+1；要数仓配合导出 |
| B. 直连库为准 | 实时 | 库一变历史报告不可复现；"同一份报告两个数"事故之源；连接凭据管理负担 |
| C. 双轨（正式用快照、监控直连） | 监控实时性 | 两套口径执行路径——正是要消灭的东西 |
| D. 什么都不定（混用） | 眼前省事 | V2 文档明令禁止：同报告混用数据源，数字必然对不上 |

## 三、决策

选择 **A**：`data/snapshots/` 存 CSV/Parquet + manifest；所有正式数字（问数/报告/回测）基于快照；慢路探查可临时连只读库，但结果必须落 raw log 并标注 `snapshot_digest=live-read`，且监控归因的"基线 vs 当前"对比必须同源。

## 四、理由

风控报告的生命周期长于任何一次数据库状态——客户三个月后问"这个数怎么来的"，只有快照能答。manifest 血缘（sha256 + data_as_of）已在 V2 实现，成本近零。

## 五、代价（必填）

- 监控归因有 T+1 时滞（秒级异常感知降为天级）——可接受：归因结论本来就要人审，不差一天。
- 数仓导出流程依赖（assumptions A-02，未验证）。
- 快照存储 12 个月滚动，约 6—12GB/主题域。

## 六、复核条件

① 出现实时性硬需求（如反欺诈在线评分——那是在线服务，不是问数系统范围）；② 数仓无法稳定导出；③ 快照体积/加载时间成为瓶颈（换 Parquet + 列裁剪）。

## 七、不懂技术的人只需确认哪一点

**"每个数字都能说清是哪天的哪份数据算出来的，三个月后还能原样重算一遍"**——这是风控报告给客户的底线，是否认可。
