# ADR-0001：语义层驱动 + 快慢双路，不用通用 Agent 框架整体承载问数

> 状态：已接受（2026-11-01）｜ 影响面：architecture 全层、spec §五、AGENTS P-03/04/05

## 一、背景

问数系统的核心矛盾：LLM 在真实数仓 schema 上的 text2sql 执行准确率公开复现仅 10—21%（Spider 2.0/BIRD 类），而风控数字错一位就是事故。候选路线有三：让通用 agent 框架自由探索、纯 RAG 检索、语义层收窄。

## 二、备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 通用 harness 自由探索（deepagents/nanobot 式） | 开发快、长任务强 | 口径决策权交给模型；错误被"任务完成率"目标函数放大；无治理概念 |
| B. 纯 RAG 检索（Vanna 式） | 实现简单、可嵌入 | 无口径收窄；公开复现 20/50；冲突口径查不出 |
| C. 语义层驱动 + 快慢双路（本决策） | 命中路径 100% 已评审口径；慢路有校验闸+人审 | 语义层建设前期重（考古+签字）；框架选型文档已详述 |
| D. 什么都不做（继续手工跑数） | 零开发成本 | 取数排队/口径事故/报告手工三大痛点原样保留 |

## 三、决策

选择 **C**：语义层 YAML 为口径宪法；快路 = enum 收窄 + 纯函数；慢路 = 固定图 + 强制人审；未晋升查询一律慢路（不做临时快路）。

## 四、理由

具体到本项目：① V2/V3 四份代码已按此架构实现并实测（9+8 场景断言）；② 风控场景"可签字"比"跑得快"重要——快路的每个数字都能回答"谁拍的口径"；③ 慢路日志是持续运营的需求来源（V3 闭环的地基）。

## 五、代价（必填）

- 语义层初始建设 2—4 周（考古 + Owner 签字），前期看不到"AI 效果"。
- 热门未晋升问题每次付 4—5 次 LLM 调用（慢路成本）。
- 新指标接入有时延（评审周期），不是"即问即得"。

## 六、复核条件

出现以下情况重启此决策：① 本地模型意图理解能力跨代（别名归一准确率 >98% 且冲突自检可靠）；② 语义层覆盖率 80% 后长尾查询形态变化；③ 组织购买商业 GenBI（WrenAI 商业版）且治理要求可被其满足。

## 七、不懂技术的人只需确认哪一点

**"没有被 Owner 签字的口径，系统不会拿它算数给人看"**——这一条是否是你对风控数字的最低要求。是，则此决策正确。
