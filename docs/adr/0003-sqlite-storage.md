# ADR-0003：运营数据用 SQLite，不上 PostgreSQL

> 状态：已接受（2026-11-01）｜ 影响面：data-model 全表、architecture §五、constraints §五

## 一、背景

运营数据（raw log/fact/评审/晋升/审计/告警）需要持久化。候选：SQLite / PostgreSQL / 文件（JSONL）。使用者 10—20 人、同时在线 3—5、单人开发（C0）、内网单机、用户明确"不懂 DBA 运维"。

## 二、备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. SQLite（Python 内置） | 零运维、备份=拷文件、单文件、单人开发友好 | 写锁单写者；无网络并发 |
| B. PostgreSQL | 并发写、pgvector 预留 | 需要安装/备份/账号体系；单人维护是负债 |
| C. JSONL 文件 | 最简单、diff 友好 | 无查询能力（热度统计/冲突检测全靠它） |
| D. 什么都不做（留内存） | 零工作 | 进程退出即失；raw log 1 年保留期无法满足 |

## 三、决策

选择 **A**：`data/ops.db` 单文件；raw log 等六表（data-model）；保留期清理走定时任务。

## 四、理由

写方只有引擎一个进程（外壳经 API/MCP，P-xx 目录约定），不存在多写者；查询模式是聚合统计（热度/指纹），SQLite 365 万行无压力；备份恢复对非 DBA 可执行。PG 的每一项优势在当前约束下都没有对应需求。

## 五、代价（必填）

- 未来若多人并发写（>5 写者）或需向量检索，须迁移 PG——迁移成本 = 数据导出 + store 层重写（约 1 周）。
- 无内置 WAL 归档级恢复，靠文件备份（每天一次，RPO 24h 可接受——运营数据可从快照+log 重建）。

## 六、复核条件

① 同时写者 >3 且出现 `database is locked`；② 接入向量检索需求（pgvector）；③ 需要跨机器读写。任一命中 → 开 ADR 评估迁移。

## 七、不懂技术的人只需确认哪一点

**"数据库坏了，最坏丢一天的运营记录，指标数字不受影响（数字在 Git 管的 YAML 和快照里）"**——这个风险可接受吗。
