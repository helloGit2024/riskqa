# 约束条件清单（constraints.md）

> **这是全套文档里唯一"无法由 AI 代劳"的部分。** AI 可以起草，但答案必须你给 ——
> 它猜出来的每一个"看起来都合理"，但都是错的。
>
> 填法：不确定的写"不确定"，不要编。编出来的约束比空着更危险。

## 一、要解决的具体问题

现状（凑合方式）与痛点，全部来自前三轮设计讨论的实证记录：

1. **口径对不上**：风控指标口径分散在约 30 个老脚本、若干 Excel 和历史报告里，无人认领。真实事故：两份报告 KS 对不上，查一周发现窗口定义不同。
2. **取数排队**：分析师问一个指标口径要走"找人 → 等排期 → 手工跑数 → 手工核对"，单个指标半天起。
3. **模型报告手工维护**：FPD30/KS/AUC/PSI 报告靠 Python 脚本 + Excel 拼装，每月重复劳动，改口径要改多处。
4. **监控归因滞后**：指标异动靠人盯日报，归因靠经验猜，结论无留痕、无确认状态。
5. **策略回测口径不可复现**：回测数字与生产口径对不上时，无法证明谁错了。

**本系统要达成的一句话说清**：语义层驱动的风控问数引擎——分析师自然语言问指标，系统走已签字口径算数（LLM 不许碰数字），慢路查询日志经"多人多次确认 + Owner 签字"沉淀为新口径，系统越用越准。

## 二、使用者

| 谁 | 人数 | 同时在线 | 在哪用 |
|---|---|---|---|
| 风控策略分析师（主要问数者） | 8—12 | 3—5 | 内网 PC，Trae / Chat2DB / CLI |
| 指标 Owner（口径签字人） | 3—5 | 1—2 | 内网 PC，评审工作台（CLI/邮件/IM） |
| 模型团队（报告场景） | 2—3 | 1—2 | 内网 PC，API 调用 |
| 值班工程师（监控归因） | 2—3 | 1 | 内网，IM 告警接收 |
| 开发者（你） | 1 | — | 开发机 + Trae |

> 同时在线按 3—5 人设计容量（R1-Q1 追问的实测答案）。无外部客户、无公网访问。

## 三、数据情况

| 项 | 内容 |
|---|---|
| 数据在哪 | ① 指标宽表快照：CSV/Parquet 文件（申请/还款/评分，内网文件服务器）；② 运营数据：SQLite（本项目目录内） |
| 大概多少 | 单主题域申请级 100 万—500 万行；快照单文件 ≤500MB |
| 增长多快 | 每月新增一份 T+1 快照；保留最近 12 个月 |
| 更新频率 | T+1（慢路探查可临时连只读库，正式交付永远基于快照） |
| 有没有敏感信息 | **有**：信贷申请/还款/评分数据，含客户身份与资金信息，按敏感数据处理（PII） |

## 四、硬约束（最重要的一节）

| 类别 | 我的硬约束 |
|---|---|
| 预算 | 零新增采购：内网单机部署，本地模型（Ollama/vLLM）优先；不买云服务、不买 BI  License |
| 合规 | **数据不出公司内网**（指标数据、raw log、证据快照、审计全部内网）；操作留痕；AI 生成内容显著标识；raw log 保留期 1 年（合规硬约束，见 V3 文档 §4.2） |
| 时间 | V4.0（工程化地基）4 周内可演示；V4.1（问数闭环）再 4 周 |
| 技术 | Python 3.13 + SQLite，内网单机可跑；不引入需要专人或云托管的组件（不上 K8s、不上 PG 集群） |

## 五、我完全不会的技术（如实写）

- **不会写前端**——本期明确不做自研前端（用户已确认），入口用 Trae / Chat2DB / CLI。
- 不懂 DBA 运维——所以选 SQLite（备份 = 拷文件），不选 PostgreSQL。
- 没做过 K8s / 容器编排——本期单机部署，运维手册按单机写。
- 风控建模 11 年、Python 工程能力强（可独立写 700 行生产代码）——架构与计算层我来，工程规范由 AI 补齐。

## 七、AI 替我做过的假设（生成文档时填，见 assumptions.md）

见 `docs/assumptions.md`。最关键三条：① 内网有可用的本地 LLM 服务（Ollama/vLLM 任一）；② 指标宽表可按 T+1 导出为文件快照；③ 使用者 10—20 人量级、无并发写冲突。

## 八、复核提醒

- 本文件的"硬约束"是方案作废线：任何一条被违反（尤其是**数据不出内网**），已交付功能作废重做。
- 使用者人数变化超过 2 倍时，重估容量设计（architecture.md 关键约束节）。
- 每次评审会后核对 Owner 产能假设（V3 文档 §10：队列积压是机制死亡首因，不是技术）。
