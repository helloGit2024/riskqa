# 归因手册（evals/attribution.md）

> 归因 = **回答"这次没答对，是哪个环节的错"**。
> 只有归因对了，才知道该改哪里——否则会陷入"到处乱改、越改越差"。
> 上游：`evals/README.md`；下游：`docs/experiments/`（每次归因后的改动都记实验）。

## 一、为什么"自动分类"不可靠

让模型自己去判断"这是我的错还是路由的错"，它会倾向于说"是路由的问题"。
**所以自动分类的结果只能叫"候选"，必须人工确认。**

## 二、对照实验法

**做法**：把"标准参数"直接喂给计算环节（跳过路由，直接指定 metric/dims/filters）。
- 给了标准参数还是算错 → **计算层/口径的问题**
- 给标准参数就答对了 → **路由/意图翻译的问题**

这是唯一能**干净地区分**"理解错"和"算错"的方法。本项目计算层是纯 Python（P-03），
算错的概率极低——**绝大多数坏例子的候选归因应该是路由或口径层**，这本身就是重要信号。

## 三、候选归因的产生规则（机器做，**只到"候选"为止**）

| 候选 | 触发条件 | 本项目对应环节 |
|---|---|---|
| `routing_wrong` | 该走快路走了慢路 / 该走慢路走了快路 | alias 索引、入口路由 |
| `intent_wrong` | 指标对但参数错（维度/过滤/时间范围） | LLM 意图翻译、FC enum 收窄 |
| `caliber_gap` | 口径没定义清楚或口径声明答反（Q011—Q014 类） | **最容易被误判成生成错**；实际是语义层/changelog 缺内容 |
| `refusal_wrong` | 该拒未拒（编造）/ 不该拒却拒（误拒） | 前闸阈值、拒答策略 |
| `verify_gap` | 校验闸没抓住（裸数字/编造引用漏网） | verify 模块——**这是真 bug，优先级最高** |
| `parse_error` | 快照加载/数据归一出错 | data 模块 |

## 四、人工确认（**不可省略的一步**）

逐条看候选 + 原始问题 + 系统完整响应（含口径返回），人工判定。
**判定标准要写下来**（同一类错，两次判定不能不一样）。

## 五、确认之后干什么（按性价比排序）

| 错误类型 | 优先动作 | 为什么 |
|---|---|---|
| `verify_gap` | 修校验闸 | 数字纪律的最后防线，漏一条都是事故 |
| `routing_wrong` | 补 alias / 修归一规则 | 纯代码改动，当天可验证 |
| `caliber_gap` | 补口径/changelog + 走 Owner 签字 | 这是"知识缺失"，改代码解决不了 |
| `intent_wrong` | 改提示词 → 换模型 | 最贵，放最后 |
| `parse_error` | 修加载/归一 | 上游错了，改下游没用 |

## 六、一轮归因的完整流程

1. 跑 `make eval`，导出坏例子（含完整响应与口径返回）；
2. 机器生成候选归因；
3. **人工逐条确认**（约 40 分钟 / 30 条）；
4. 按候选分组，统计各类占比；
5. 按性价比排序，挑一类先改；
6. 改完重跑同一套题库，写进 `docs/experiments/`。

## 七、两个经常被搞混的问题

| 问题 | 区别 |
|---|---|
| "分数低是因为题难还是系统差" | 看**同类题的通过率**，不看平均分 |
| "改了之后分数涨了是真的吗" | 单次差异不算数，要 **≥3 次**且差异大于波动 |

## 八、与需求文档的差异（记录在此，避免以后重复讨论）

| 差异 | 需求文档怎么说 | 实际怎么做 | 为什么 |
|---|---|---|---|
| 无检索层 | 模板含 Recall@k 检索指标 | 删除检索指标，改路由准确率 + alias 命中率 | 本项目语义层精确匹配 + SQL schema 链接，没有向量检索（V4.3 前不引入） |
| 数字类评分 | 模板要求"数字类必须人工评" | 数字类走规则硬指标（结果集机器比对），人工只终判拒答类 | 计算层纯 Python，ground truth 可由纯函数复算——机器比人可靠且零成本；裁判只用于叙事类 |
| 归因候选 | 模板五类（retrieval_miss 等） | 改成本项目六类（routing_wrong 等，见 §三） | 环节不同：本项目是"路由→快/慢路→校验闸→治理"，不是"检索→生成" |
