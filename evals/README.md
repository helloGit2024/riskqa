# 评估说明（evals/README.md）

> 本项目是模型应用（LLM 进编排层与叙事层），所以 `evals/` 保留。
> 上游：`docs/spec.md` §3.2（质量验收数字）；下游：`docs/tasks.md` T-4.1.8（runner）/ T-4.3.5（扩容）。
> 硬规则依据：`AGENTS.md` P-17（失败场景 FakeLLM 脚本化）、第五节禁止清单（不许改题）。

## 一、为什么"传统测试"不够用

传统测试测的是"输入 A 是否得到输出 B"，**结果确定**。
而本系统的输出**不确定**：同一个"各渠道 FPD30"，LLM 可能路由错指标、选错维度、把口径答反；
该拒答的时候可能编一个数字。这三件事，单元测试一个都测不出来——所以有 `golden_set.yaml`。

**本项目的特殊性**：计算层是纯 Python（P-03），所以"数字对不对"可以用**规则硬指标**机器判；
需要裁判的只有叙事与口径声明。这把评估成本压到了最低。

## 二、评估指标（三层）

### 第 1 层：路由质量（问数系统的第一道关）

| 指标 | 含义 | 目标 |
|---|---|---|
| 路由准确率 | 该走快路的走了快路、该走慢路的走了慢路 | ≥95%（黄金题集 route 字段比对） |
| alias 命中率 | 口语问法（"首期逾期"）归一到标准指标 | ≥95%（T-4.1.1 验收） |

### 第 2 层：结果质量（前提是路由已对）

| 指标 | 含义 | 目标 |
|---|---|---|
| 结果集正确率 | 比结果集（行序/列序/列名无关，容差 1e-6） | ≥95%（spec §3.2） |
| 口径声明正确 | 对抗口径题（Q011—Q014）按签字口径回答 | 100%（6 题全过） |
| 数字精确性 | 叙事层数字与 FactStore 一致 | 必须 100%（校验闸已兜底，这里复核） |

### 第 3 层：端到端体验

| 指标 | 含义 | 目标 |
|---|---|---|
| 回答正确率 | 人工判定的整体满意度 | ≥95% |
| 拒答正确率 / 误拒率 | 见下节 | 100% / <5% |

## 三、"应拒答"类怎么评分（重点）

必须**同时**设两个指标，缺一个就会走偏：

| 指标 | 定义 | 只看它的后果 |
|---|---|---|
| 拒答正确率 | 该拒答的题里（Q017—Q020），真的拒答的比例 | 只看它 → 系统会变得"什么都不敢答" |
| 误拒率 | 本该回答的题里（Q001—Q016），被拒答的比例 | 只看它 → 系统会变得"什么都说" |

> 一个只知道拒答的系统，拒答正确率 100%，但完全没用。**这两个指标必须一起看。**
> 本项目的门禁取值（spec §3.2 / releases V4.1）：拒答类 **100%（无容差）**，误拒 <5%。

**拒答类的评分方式**：runner 先机器预筛（响应无 result_set + 带拒答标记 + 不含禁列数字），
人工终判（scoring: human）——因为"拒答的理由是否充分"机器判不了。

## 四、怎么跑评估

```bash
make eval        # V4.1 起可用（runner 见 tasks.md T-4.1.8）
```

**可复现性的三个前提**（缺一个，每次跑的结果都不一样，就没法对比）：

1. **题库冻结**：版本号 + 冻结日期写在 `golden_set.yaml` 的 `meta:` 里（当前 0.1.0 / 2026-11-01）；
2. **时间冻结**："上个月"这类相对时间以 `meta.frozen_now`（2026-11-01T10:00:00）为基准解析；
3. **模型参数固定**：评估一律走 FakeLLM 脚本（P-17，零 token、确定性），真模型只做抽检校准，temperature=0。

**种子数据**：`evals/seed.sql`（fact_application 1200 行 + dim_channel 3 行），
由 legacy V2 演示数据生成器（numpy seed=42, n=1200）确定性生成；
期望值全部由 seed 上的 Python 纯函数算出并留档。重建方式：legacy 存档 + 同参数生成器落库。

## 五、自动评分怎么做（LLM-as-Judge）

见 `judge-prompt.md`。**必须遵守的四条**：

1. 裁判模型与被评模型**不能是同一个**（否则会自己给自己高分）；
2. 裁判提示词必须**版本化**（改了就记版本号）；
3. 每次评估都要**人工校准**一批（抽 10—20 条人工评，看和裁判的差距）；
4. **数字类、拒答类不交给裁判**：数字类走规则硬指标（结果集机器比对，零成本），拒答类人工终判。
   裁判只用于叙事质量类（V4.3 报告场景起）。

## 六、归因

见 `attribution.md`。评估不达标时的标准动作：跑归因 → 按性价比排序改 → 重跑同一套题库 → 写实验记录。

## 七、★ 评估口径 vs 线上口径（两个数字不可混用）

| | 评估口径 | 线上口径 |
|---|---|---|
| 题目来源 | 冻结的题库（20 题，V4.3 起 50 题） | 真实用户提问 |
| 能用来… | 判断"这次改动是进步还是退步" | 判断"线上实际好不好用" |
| 不能用来… | 对外汇报"我们准确率 XX%" | 做版本对比 |

> 混用会得出相反的结论——例如评估涨了但线上跌了（因为真实提问分布变了）。
> 20 题是回归基线不是成绩单；题目会随线上坏例回流增长，通过率的分母随之变化，
> 所以版本对比必须同版本号题库（见 §八）。

## 八、评估集的维护规则

### 什么时候加题

- 线上出现了一个新的坏例子 → 加一条（**这是最主要的上题来源**）；
- 每次口径晋升（新指标/新 alias）→ 补该指标的题。

### 加题 / 改题 / 删题

- 加题：随便加，不影响历史对比（新题不参与老版本的重跑）；
- 改题：**必须先冻结一个新版本号**，改完标注"从版本 X 起生效"；
- 删题：**绝对禁止**。

### 为什么"为了让评估通过而删题"是绝对禁止的

因为那等于**给考试改分数**。这个系统的全部价值建立在"这个数字是真的"之上。
一旦发现一次作弊，整套评估就作废了。此条已写入 `AGENTS.md` 第五节禁止清单，无例外。
